# What is a Database Router?

A Database Router is responsible for deciding

which database should execute a query.

Instead of

```text id="dbrt002"
FastAPI

↓

Primary
```

we have

```text id="dbrt003"
FastAPI

↓

Database Router

↓

Primary

Replica 1

Replica 2

Replica 3
```

Every request goes through the router.

______________________________________________________________________

# Why Is This Better?

Without Router

```python
if operation == "read":
    ...

if operation == "write":
    ...

if operation == "read":
    ...
```

Every repository duplicates routing logic.

______________________________________________________________________

With Router

```python
session = router.get_read_session()
```

Much cleaner.

# Create Engines

```python id="dbrt006"
from sqlalchemy import create_engine

write_engine = create_engine(
    PRIMARY_DB
)

read_engines = [

    create_engine(REPLICA_1),

    create_engine(REPLICA_2)

]
```

______________________________________________________________________

# Why Multiple Read Engines?

Because

```text id="dbrt007"
Replica 1

↓

Busy

Replica 2

↓

Idle
```

We can distribute traffic.

______________________________________________________________________

# Database Router Class

```python id="dbrt008"
from sqlmodel import Session

import random


class DatabaseRouter:

    def __init__(

        self,

        write_engine,

        read_engines

    ):

        self.write_engine = write_engine

        self.read_engines = read_engines
```

______________________________________________________________________

# Read Session

```python id="dbrt009"
    def get_read_session(

        self

    ):

        engine = random.choice(

            self.read_engines

        )

        return Session(engine)
```

This example uses random selection to keep the implementation simple. In production, you might use round-robin,
health-aware routing, or load-based selection.

______________________________________________________________________

# Write Session

```python id="dbrt010"
    def get_write_session(

        self

    ):

        return Session(

            self.write_engine

        )
```

All writes always go to the Primary.

______________________________________________________________________

# Create Router

```python id="dbrt011"
router = DatabaseRouter(

    write_engine,

    read_engines

)
```

______________________________________________________________________

# Reading Data

```python id="dbrt012"
with router.get_read_session() as session:

    user = session.get(

        User,

        10

    )
```

The router automatically chooses a Replica.

______________________________________________________________________

# Writing Data

```python id="dbrt013"
with router.get_write_session() as session:

    user = User(

        name="Alice"

    )

    session.add(user)

    session.commit()
```

The write always goes to the Primary.

______________________________________________________________________

# Repository Layer

Repository

# Read-After-Write Problem

Suppose

```python

↓

```

If

`get_user()`

the new user may not appear immediately because of replication lag.

# Sticky Reads

One solution

```text id="dbrt020"

↓

↓
```

# Common Mistakes

### Reading from the Primary

Every read increases Primary load.

Use Replicas whenever appropriate.

______________________________________________________________________

### Writing to Replicas

Writes belong on the Primary.

______________________________________________________________________

### Hardcoding Database Selection

Centralize routing logic.

______________________________________________________________________

### Ignoring Replica Health

Always verify the selected replica is available.

______________________________________________________________________

# Best Practices

- Keep routing centralized.
- Repositories should not know about replicas.
- Services should request read or write sessions.
- Use connection pools.
- Monitor replica health.
- Log routing decisions.
- Handle replication lag for read-after-write scenarios.

# Interview Deep Dive

## Answer

**Question:** Why should database routing be implemented in a dedicated router instead of inside repositories?

Repositories should focus only on data access, not infrastructure decisions. A dedicated router centralizes database
selection, making the application easier to maintain and extend. If new replicas are added or routing rules change, only
the router needs to be updated, while repositories and business logic remain unchanged.

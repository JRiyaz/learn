# Database Scaling Masterclass - Part 1

# Why Databases Become Bottlenecks

______________________________________________________________________

## Introduction

So far in this roadmap, every project has looked like this:

```text
                FastAPI

                   │

                   ▼

             PostgreSQL
```

This architecture works perfectly for:

- Personal projects
- Small startups
- Internal tools
- MVPs

But what happens when your application grows?

Suppose your application now has:

- 5 million users
- 50,000 requests/sec
- Hundreds of API servers
- Terabytes of data

Can one PostgreSQL server still handle everything?

Usually...

**No.**

This chapter explains why.

# CPU Bottleneck

Consider

```sql
SELECT *

FROM orders

WHERE customer_id = 100;
```

PostgreSQL must

- Parse SQL
- Build execution plan
- Search indexes
- Filter rows
- Build result

All of this consumes CPU.

______________________________________________________________________

Suppose

100 users

↓

100 queries

No problem.

Suppose

100,000 users

↓

100,000 queries

CPU usage may reach

```text
100%
```

Now requests become slower.

______________________________________________________________________

# Memory Bottleneck

Databases use memory for

- Cache
- Buffers
- Sorting
- Hash joins
- Temporary tables

Imagine

```text
RAM

32 GB
```

Your database

```text
400 GB
```

Obviously

everything cannot fit in memory.

Now PostgreSQL must read from disk much more often.

______________________________________________________________________

# Disk Bottleneck

Disk is much slower than RAM.

Approximate access times:

| Storage | Approximate Access Time |
| --------- | ----------------------: |
| CPU Cache | ~1 ns |
| RAM | ~100 ns |
| NVMe SSD | ~100 µs |
| HDD | ~5–10 ms |

Even modern SSDs are thousands of times slower than RAM.

This is why databases try to cache frequently accessed data.

______________________________________________________________________

Example

```text
RAM

↓

Fast

Disk

↓

Slow
```

______________________________________________________________________

# Network Bottleneck

Application

↓

Database

↓

Network

Suppose

every request returns

```text
20 MB
```

Network bandwidth eventually becomes a bottleneck.

Sometimes

the database itself is fast,

but sending results over the network is slow.

______________________________________________________________________

# Connection Bottleneck

Every client needs a connection.

Imagine

```text
1000

Clients
```

PostgreSQL

```text
max_connections = 100
```

Only

100

connections are allowed.

The remaining clients wait.

______________________________________________________________________

Without connection pooling

```text
Client

↓

Open Connection

↓

Query

↓

Close Connection
```

Repeated thousands of times.

This is expensive.

______________________________________________________________________

With connection pooling

```text
Clients

↓

Connection Pool

↓

Database
```

Connections are reused.

______________________________________________________________________

# Lock Contention

Suppose

two users modify

the same row.

```text
User A

↓

UPDATE Account
```

At the same time

```text
User B

↓

UPDATE Account
```

One transaction waits.

As traffic increases,

lock contention increases.

______________________________________________________________________

# Large Tables

Imagine

Orders

```text
10 rows
```

Very fast.

Now

```text
500 million rows
```

Even with indexes,

Maintenance also becomes harder.

______________________________________________________________________

# Expensive Queries

Bad query

```sql
SELECT *

FROM orders;
```

On

500 million rows.

Not ideal.

Better

```sql
SELECT id,
       total_amount

FROM orders

WHERE customer_id = 10

LIMIT 20;
```

Retrieve only the columns and rows you actually need.

______________________________________________________________________

# Missing Indexes

Without index

```sql
SELECT *

FROM users

WHERE email='a@example.com';
```

Database

↓

Reads

every row.

With index

↓

Direct lookup.

Huge difference.

# Too Many Writes

Imagine

```text
100

Writes/sec
```

No issue.

Now

```text
50,000

Writes/sec
```

Every write

- Updates indexes
- Writes WAL
- Flushes data
- Acquires locks

# Common Symptoms of Database Bottlenecks

You may notice:

- Slow API responses
- High CPU usage
- High memory usage
- Long-running queries
- Connection timeouts
- Lock waits
- Slow reports
- Increased latency

These are often signs that the database needs optimization or scaling.

______________________________________________________________________

# Monitoring Metrics

Always monitor:

- CPU Usage
- Memory Usage
- Active Connections
- Query Latency
- Slow Queries
- Cache Hit Ratio
- Disk I/O
- WAL Generation
- Locks
- Replication Lag (if replicas exist)

Good monitoring helps identify problems before users notice them.

______________________________________________________________________

# Common Mistakes

### Using `SELECT *`

Retrieve only the columns you need.

______________________________________________________________________

### Missing Indexes

Indexes should support common query patterns.

______________________________________________________________________

### Opening New Connections

Use connection pools.

______________________________________________________________________

### Ignoring Slow Queries

Analyze them with:

```sql
EXPLAIN ANALYZE
```

______________________________________________________________________

### Assuming One Database Is Enough Forever

Every successful application eventually needs to consider scaling.

______________________________________________________________________

# Best Practices

- Optimize queries first.
- Add indexes where appropriate.
- Use pagination.
- Monitor database metrics.
- Reuse connections.
- Cache expensive reads.
- Scale only after understanding the bottleneck.

# Interview Deep Dive

## Answer

**Question:** My application's database is becoming slow. What should I do first?

The first step is to identify the actual bottleneck rather than immediately adding more hardware. I would examine slow
query logs, use `EXPLAIN ANALYZE` to understand query execution plans, check CPU, memory, disk I/O, connection usage,
lock contention, and cache hit ratios. In many cases, optimizing queries, adding appropriate indexes, improving
connection pooling, or caching frequently accessed data provides much greater benefit than scaling the database itself.

# Database Scaling Masterclass - Part 4

# Read Replicas (Primary-Replica Architecture)

______________________________________________________________________

# Introduction

In the previous lecture, we learned about **Horizontal Scaling**.

One of the first techniques companies adopt is **Read Replication**.

Why?

Because in most applications,

**reads greatly outnumber writes**.

For example,

Instagram

```text id="dbr001"
Upload Photo

↓

1 Write
```

But

```text id="dbr002"
View Photo

↓

10 Million Reads
```

The database spends most of its time serving **read queries**, not writes.

Read Replicas solve this problem.

______________________________________________________________________

# What is a Read Replica?

A Read Replica is a copy of the primary database.

Architecture

```text id="dbr003"
                 Primary

              (Read + Write)

                    │

      ┌─────────────┴─────────────┐

      ▼                           ▼

Replica 1                   Replica 2

(Read Only)                (Read Only)
```

The application:

- Sends **writes** to the Primary.
- Sends **reads** to Replicas.

______________________________________________________________________

# Why Does This Help?

Suppose

```text id="dbr004"
10 Writes/sec

100,000 Reads/sec
```

Instead of

```text id="dbr005"
100,010 Queries

↓

One Database
```

We distribute the load.

```text id="dbr006"
Writes

↓

Primary

Reads

↓

Replica 1

↓

Replica 2

↓

Replica 3
```

Now each server handles fewer requests.

______________________________________________________________________

# Primary Database

The Primary handles

- INSERT
- UPDATE
- DELETE
- ALTER TABLE
- CREATE INDEX
- Transactions

Example

```sql id="dbr007"
INSERT INTO users

(name)

VALUES

('Riyaz');
```

Always goes to

```text id="dbr008"
Primary
```

______________________________________________________________________

# Replica Database

Replicas handle

```sql id="dbr009"
SELECT *

FROM users;
```

Read-only operations.

Attempting to write to a replica should fail.

______________________________________________________________________

# Data Replication

How does Replica receive data?

```text id="dbr010"
Application

↓

Primary

↓

Replication

↓

Replica
```

The database continuously copies changes from the Primary to the Replicas.

This process is automatic once replication is configured.

______________________________________________________________________

# Synchronous vs Asynchronous Replication

There are two common replication strategies.

## Synchronous Replication

```text id="dbr011"
Write

↓

Primary

↓

Replica

↓

Success
```

The Primary waits for the Replica before confirming the write.

Advantages

- Stronger consistency

Disadvantages

- Higher write latency
- Slower writes

______________________________________________________________________

## Asynchronous Replication

```text id="dbr012"
Write

↓

Primary

↓

Success

↓

Replica Later
```

The application gets a faster response.

Replication happens afterward.

Advantages

- Faster writes
- Better throughput

Disadvantages

Replica may briefly lag behind.

Most production systems use asynchronous replication for general workloads.

______________________________________________________________________

# Replication Lag

Suppose

```sql id="dbr013"
INSERT INTO users

VALUES ('Alice');
```

Immediately afterward,

```sql id="dbr014"
SELECT *

FROM users;
```

The query is sent to Replica.

Replica

↓

Hasn't received the update yet.

Result

```text id="dbr015"
No Row Found
```

This is called

```text id="dbr016"
Replication Lag
```

______________________________________________________________________

# Read-After-Write Consistency

Consider

User updates profile.

Immediately refreshes the page.

```text id="dbr017"
Update Profile

↓

Read Profile
```

If the read goes to a lagging Replica,

the user may see stale data.

______________________________________________________________________

# Solution 1

Read from Primary

for a short period after a write.

```text id="dbr018"
Write

↓

Primary

↓

Next Read

↓

Primary
```

______________________________________________________________________

# Solution 2

Wait briefly

before reading.

Usually,

applications prefer Solution 1.

______________________________________________________________________

# Read Routing

Our application now needs a router.

```text id="dbr019"
Application

↓

Database Router

↓

Read?

↓

Replica

Write?

↓

Primary
```

Business logic remains unchanged.

______________________________________________________________________

# Python Configuration

Suppose

```python id="dbr020"
PRIMARY_DATABASE = (
    "postgresql://primary-db/library"
)

REPLICA_DATABASE = (
    "postgresql://replica-db/library"
)
```

Create two SQLAlchemy engines.

```python id="dbr021"
from sqlalchemy import create_engine

write_engine = create_engine(
    PRIMARY_DATABASE
)

read_engine = create_engine(
    REPLICA_DATABASE
)
```

______________________________________________________________________

# Read Session

```python id="dbr022"
from sqlmodel import Session

def get_read_session():

    with Session(
        read_engine
    ) as session:

        yield session
```

______________________________________________________________________

# Write Session

```python id="dbr023"
def get_write_session():

    with Session(
        write_engine
    ) as session:

        yield session
```

______________________________________________________________________

# Repository Example

Read

```python id="dbr024"
def get_user(

    session,

    user_id

):

    return session.get(
        User,
        user_id
    )
```

Write

```python id="dbr025"
def create_user(

    session,

    user

):

    session.add(user)

    session.commit()
```

The repository doesn't care whether it's using the Primary or Replica.

The caller provides the appropriate session.

______________________________________________________________________

# Load Balancing Reads

Suppose

three replicas exist.

```text id="dbr026"
Replica 1

Replica 2

Replica 3
```

The router can distribute requests.

Example

```text id="dbr027"
Request 1

↓

Replica 1

Request 2

↓

Replica 2

Request 3

↓

Replica 3
```

This balances the workload.

______________________________________________________________________

# Replica Failure

Suppose

Replica 2 crashes.

```text id="dbr028"
Replica 2

↓

Offline
```

The router redirects reads to the remaining replicas.

The application continues working.

______________________________________________________________________

# Primary Failure

Suppose

Primary crashes.

```text id="dbr029"
Primary

↓

Offline
```

Now

writes stop.

Most production systems perform

**automatic failover**,

promoting a Replica to become the new Primary.

We'll discuss high availability later.

# Advantages

Read Replicas provide:

- Higher read throughput
- Better availability
- Reduced load on the Primary
- Easier scaling
- Simpler architecture than sharding

______________________________________________________________________

# Disadvantages

Read Replicas also introduce:

- Replication lag
- More servers to manage
- Routing complexity
- Failover considerations

______________________________________________________________________

# Common Mistakes

### Writing to a Replica

Writes should always go to the Primary.

______________________________________________________________________

### Ignoring Replication Lag

Users may read stale data.

______________________________________________________________________

### Sending Every Read to the Primary

This defeats the purpose of replicas.

______________________________________________________________________

### Hardcoding Database Selection

Centralize routing logic.

______________________________________________________________________

# Best Practices

- Keep writes on the Primary.
- Route reads to Replicas.
- Monitor replication lag.
- Handle replica failures gracefully.
- Keep routing logic in one place.
- Use connection pools for every database.

# Interview Deep Dive

## Answer

**Question:** A user updates their profile and immediately refreshes the page but sees the old data. Why?

The application is likely using a read replica with asynchronous replication. The update was written to the Primary, but
the Replica hasn't received the change yet because of replication lag. A common solution is to route read-after-write
requests to the Primary for a short period or until consistency is guaranteed.

# Database Scaling Masterclass - Part 3

# Horizontal Scaling (Scaling Out)

______________________________________________________________________

## Introduction

In the previous lecture, we learned about **Vertical Scaling**.

Vertical scaling works well for a long time.

But eventually you'll reach a point where one database server is no longer enough.

At that point, instead of making the server bigger,

you add **more servers**.

This is called **Horizontal Scaling**.

______________________________________________________________________

# What is Horizontal Scaling?

Horizontal Scaling means adding **multiple database servers** instead of upgrading a single one.

Instead of this

```text id="dbhs001"
FastAPI

↓

PostgreSQL
```

we move to

```text id="dbhs002"
                 FastAPI

                    │

        ┌───────────┼───────────┐

        ▼           ▼           ▼

      DB-1        DB-2        DB-3
```

Now the workload is distributed.

______________________________________________________________________

# Why Horizontal Scaling?

Imagine your application has

```text id="dbhs003"
20 Million Users
```

A single server cannot handle

- Reads
- Writes
- Storage
- Connections

Adding more servers increases capacity.

______________________________________________________________________

# Scale Up vs Scale Out

Vertical Scaling

```text id="dbhs004"
One Bigger Server
```

Horizontal Scaling

```text id="dbhs005"
Many Smaller Servers
```

______________________________________________________________________

# Real Example

Imagine an e-commerce website.

Instead of

```text id="dbhs006"
One PostgreSQL Server
```

you have

```text id="dbhs007"
Orders Database

Users Database

Payments Database

Analytics Database
```

Different workloads are distributed.

______________________________________________________________________

# Benefits

Horizontal Scaling provides:

- Higher throughput
- More storage
- More connections
- Better availability
- Better fault tolerance
- Easier future growth

______________________________________________________________________

# But...

Adding servers creates new challenges.

Questions arise:

- Which server stores my data?
- Which server should receive my query?
- How do I keep data synchronized?
- What happens if a server fails?

These are the problems we'll solve throughout this module.

______________________________________________________________________

# Types of Horizontal Scaling

There are four major techniques.

```text id="dbhs008"
Horizontal Scaling

│

├── Read Replicas

├── Sharding

├── Partitioning

└── Multi-Database Design
```

We'll study each individually.

______________________________________________________________________

# Read Replicas

One server handles writes.

Multiple servers handle reads.

```text id="dbhs009"
              Primary

                 │

      ┌──────────┴──────────┐

      ▼                     ▼

 Read Replica 1      Read Replica 2
```

This is ideal when reads greatly outnumber writes.

We'll cover this in the next lecture.

______________________________________________________________________

# Sharding

Instead of copying all data,

split it.

Example

```text id="dbhs010"
Users

1-1,000,000

↓

DB-1

Users

1,000,001-2,000,000

↓

DB-2
```

Each database stores only part of the data.

______________________________________________________________________

# Partitioning

Unlike sharding,

partitioning usually occurs **inside one database server**.

Example

```text id="dbhs011"
Orders

2023

↓

Partition 1

Orders

2024

↓

Partition 2
```

The application still connects to one database.

The database decides which partition to use.

______________________________________________________________________

# Multi-Database Design

Large companies often separate databases by business domain.

```text id="dbhs012"
User Database

Inventory Database

Orders Database

Billing Database
```

Each service owns its own data.

This approach is common in microservices.

______________________________________________________________________

# Horizontal Scaling Does NOT Mean Everything Is Distributed

Many people think

```text id="dbhs013"
Multiple Databases

=

Sharding
```

Not necessarily.

You may simply have

- Primary
- Replica

which is also horizontal scaling.

______________________________________________________________________

# Application Changes

With one database

```python id="dbhs014"
engine = create_engine(
    DATABASE_URL
)
```

Simple.

With multiple databases,

your application must decide

which database to use.

This is called **Database Routing**.

We'll build one later.

______________________________________________________________________

# Example Router

```text id="dbhs015"
Application

↓

Database Router

↓

Choose Database

↓

Execute Query
```

Instead of every repository deciding,

one routing layer makes the decision.

# New Challenges

Horizontal scaling introduces new problems.

### Data Consistency

Suppose

```text id="dbhs016"
Write

↓

Primary
```

Read

↓

Replica

The replica may not yet contain the latest data.

This is called **Replication Lag**.

______________________________________________________________________

### Distributed Transactions

Suppose

Money transfer

```text id="dbhs017"
User DB

↓

Payment DB
```

How do we ensure both succeed?

Traditional ACID transactions no longer span multiple independent databases automatically.

We'll study distributed transactions later.

______________________________________________________________________

### Routing

Suppose

Customer ID

```text id="dbhs018"
1250
```

Which database stores this customer?

Your application must know.

______________________________________________________________________

### Monitoring

Instead of monitoring

one database,

you now monitor

```text id="dbhs019"
DB-1

DB-2

DB-3

Replica-1

Replica-2
```

Operational complexity increases.

______________________________________________________________________

# Failure Handling

Imagine

DB-2 crashes.

Can users continue?

It depends on your architecture.

A good horizontally scaled system should continue operating where possible, with degraded functionality rather than
complete failure.

______________________________________________________________________

# Advantages

Horizontal scaling offers:

- Higher capacity
- Better fault tolerance
- Easier future growth
- Reduced load per server
- Potential for higher availability

______________________________________________________________________

# Disadvantages

Horizontal scaling also brings:

- More complexity
- Routing logic
- Data synchronization
- Operational overhead
- Distributed systems challenges

It is powerful,

but not free.

______________________________________________________________________

# When Should You Use It?

Horizontal scaling is appropriate when:

- Vertical scaling is no longer sufficient.
- Read or write traffic exceeds a single server's capacity.
- High availability is required.
- Storage requirements exceed one server.
- The application continues growing.

# Common Mistakes

### Starting with Sharding

Don't introduce distributed complexity before it's needed.

______________________________________________________________________

### Ignoring Monitoring

Multiple databases require better observability.

______________________________________________________________________

### Assuming More Servers Automatically Improve Performance

The architecture and query patterns still matter.

______________________________________________________________________

### Forgetting About Consistency

Distributed databases require careful consistency planning.

______________________________________________________________________

# Best Practices

- Scale only after measuring bottlenecks.
- Start with vertical scaling.
- Add read replicas before sharding when appropriate.
- Keep routing logic centralized.
- Monitor every database instance.
- Understand the trade-offs before introducing distributed systems.

# Interview Deep Dive

## Answer

**Question:** When would you choose horizontal scaling over vertical scaling?

I would first optimize queries and indexes, then use vertical scaling because it's simpler and requires no architectural
changes. When a single server can no longer handle the required read traffic, write traffic, storage, or availability
requirements, I would move to horizontal scaling. The first step is often adding read replicas, followed by techniques
such as sharding or service-specific databases if growth continues.

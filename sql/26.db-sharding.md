# Database Sharding

______________________________________________________________________

# Introduction

So far, we've learned:

- Vertical Scaling
- Horizontal Scaling
- Read Replicas
- Database Router

All of these still assume **every database contains all the data**.

With Read Replicas,

```text id="dbsh001"
Primary

↓

Replica 1

↓

Replica 2
```

Every database stores

**every user**

**every order**

**every product**

Sooner or later,

this becomes impossible.

Imagine

```text id="dbsh002"
Users

500 Million
```

One database may simply be too large.

This is where **Sharding** comes in.

______________________________________________________________________

# What is Sharding?

Sharding means splitting data across **multiple independent databases**.

Instead of

```text id="dbsh003"
DB-1

Users

1-500 Million
```

we split

```text id="dbsh004"
DB-1

Users

1-100 Million

DB-2

Users

100-200 Million

DB-3

Users

200-300 Million
```

Each database stores only a portion of the data.

______________________________________________________________________

# Why Sharding?

Without sharding

```text id="dbsh005"
One Database

↓

4 TB
```

After sharding

```text id="dbsh006"
DB-1

1 TB

DB-2

1 TB

DB-3

1 TB

DB-4

1 TB
```

Each server stores less data.

______________________________________________________________________

# Read Replicas vs Sharding

Read Replicas

```text id="dbsh007"
Same Data

↓

Multiple Servers
```

Sharding

```text id="dbsh008"
Different Data

↓

Multiple Servers
```

This is the biggest difference.

______________________________________________________________________

# Example

Users

```text id="dbsh009"
User 1

↓

Shard A

User 2

↓

Shard B

User 3

↓

Shard C
```

Each user exists on only one shard.

______________________________________________________________________

# Shard Key

Every sharded database needs a

```text id="dbsh010"
Shard Key
```

The Shard Key determines

which database stores the data.

Examples

- User ID
- Customer ID
- Tenant ID
- Region

Choosing the correct shard key is one of the most important design decisions.

______________________________________________________________________

# Hash-Based Sharding

Suppose

```text id="dbsh011"
4 Shards
```

Algorithm

```text id="dbsh012"
User ID

%

4
```

Example

User

```text id="dbsh013"
25

↓

25 % 4

↓

1

↓

Shard 1
```

User

```text id="dbsh014"
82

↓

82 % 4

↓

2

↓

Shard 2
```

Simple.

Fast.

Even distribution.

______________________________________________________________________

# Python Example

```python id="dbsh015"
NUMBER_OF_SHARDS = 4


def get_shard(

    user_id

):

    return user_id % NUMBER_OF_SHARDS
```

Example

```python id="dbsh016"
get_shard(25)

# 1

get_shard(82)

# 2
```

______________________________________________________________________

# Range-Based Sharding

Instead of hashing,

use ranges.

```text id="dbsh017"
Users

1-1 Million

↓

Shard 1

Users

1M-2M

↓

Shard 2
```

Simple.

Easy to understand.

______________________________________________________________________

# Problem

Suppose

Most users

are

```text id="dbsh018"
1-1 Million
```

Shard 1 becomes overloaded.

Other shards remain mostly idle.

This is called a **hot shard**.

# Tenant-Based Sharding

# Shard Router

Instead of

```python id="dbsh023"
engine = create_engine(

    DATABASE_URL

)
```

we choose

```python id="dbsh024"
engine = router.get_engine(

    user_id

)
```

The router determines

the correct database.

______________________________________________________________________

# Example Router

```python id="dbsh025"
class ShardRouter:

    def __init__(

        self,

        engines

    ):

        self.engines = engines

    def get_engine(

        self,

        user_id

    ):

        shard = user_id % len(

            self.engines

        )

        return self.engines[shard]
```

# Cross-Shard Queries

Suppose

Find

```text id="dbsh027"
All Users
```

Problem

Data exists in

```text id="dbsh028"
Shard 1

Shard 2

Shard 3

Shard 4
```

The application must query every shard and combine the results.

These queries are more expensive than querying a single database.

______________________________________________________________________

# Joins

Suppose

Users

↓

Shard 1

Orders

↓

Shard 2

Can we write

```sql id="dbsh029"
SELECT *

FROM users

JOIN orders
```

Not directly across independent PostgreSQL servers.

Applications usually:

- Keep related data together, or
- Perform joins in application code, or
- Use specialized distributed database technologies.

______________________________________________________________________

# Adding More Shards

Suppose

4 shards

↓

Need

8 shards.

What happens?

The hash

```text id="dbsh030"
user_id % 4
```

changes to

```text id="dbsh031"
user_id % 8
```

Almost every user maps to a different shard.

Data migration becomes necessary.

This is one reason consistent hashing exists, which we'll discuss later.

______________________________________________________________________

# Advantages

Sharding provides:

- More storage
- More write throughput
- Better scalability
- Smaller databases
- Better isolation

______________________________________________________________________

# Disadvantages

Sharding introduces:

- Routing logic
- Cross-shard queries
- Data migration
- Operational complexity
- More difficult transactions

______________________________________________________________________

# Common Mistakes

### Poor Shard Key

A bad shard key creates uneven load.

______________________________________________________________________

### Cross-Shard Joins

These are expensive and should be minimized.

______________________________________________________________________

### Ignoring Future Growth

Plan for adding more shards.

______________________________________________________________________

### Using Sharding Too Early

Most applications don't need sharding initially.

______________________________________________________________________

# Best Practices

- Choose the shard key carefully.
- Keep related data together.
- Minimize cross-shard queries.
- Centralize shard routing.
- Monitor shard utilization.
- Plan for future shard expansion.

# Interview Deep Dive

## Answer

**Question:** Why is selecting the shard key one of the most important decisions in a sharded database?

The shard key determines where every record is stored. A good shard key distributes data and traffic evenly across
shards while keeping related data together. A poor choice can create hot shards, uneven storage utilization, expensive
cross-shard queries, and difficult future migrations. Changing the shard key later is often a complex and expensive
operation.

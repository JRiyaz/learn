# Database Scaling Masterclass - Part 2

# Vertical Scaling (Scaling Up)

______________________________________________________________________

## Introduction

In the previous lecture, we learned **why databases become bottlenecks**.

Now the obvious question is:

> "Why not just buy a bigger server?"

The answer is:

**Sometimes you should.**

This approach is called **Vertical Scaling**.

It is the simplest way to improve database performance and is usually the **first scaling strategy** companies adopt.

______________________________________________________________________

# What is Vertical Scaling?

Vertical Scaling means increasing the resources of a **single database server**.

Instead of adding more database servers,

you upgrade the existing one.

```text id="dbvs001"
Small Server

↓

Bigger Server
```

______________________________________________________________________

# Example

Before

```text id="dbvs002"
CPU

4 Cores

RAM

8 GB

Storage

500 GB SSD
```

After

```text id="dbvs003"
CPU

32 Cores

RAM

128 GB

Storage

4 TB NVMe SSD
```

Same database.

Better hardware.

______________________________________________________________________

# Architecture

Before

```text id="dbvs004"
FastAPI

↓

PostgreSQL
```

After

```text id="dbvs005"
FastAPI

↓

More Powerful PostgreSQL
```

Nothing changes in your application.

______________________________________________________________________

# Why Does It Work?

A stronger server means:

- More CPU cores
- More RAM
- Faster disks
- Higher network bandwidth

Every database operation becomes faster.

______________________________________________________________________

# More CPU

Suppose PostgreSQL executes

```sql id="dbvs006"
SELECT *

FROM orders

WHERE customer_id = 100;
```

A faster CPU:

- Parses SQL faster
- Executes joins faster
- Builds execution plans faster
- Processes more concurrent queries

______________________________________________________________________

# More RAM

Imagine

Database size

```text id="dbvs007"
200 GB
```

Server RAM

```text id="dbvs008"
16 GB
```

Most data must be read from disk.

Upgrade

```text id="dbvs009"
256 GB RAM
```

Now much more data fits into memory.

Disk access decreases dramatically.

______________________________________________________________________

# Faster Storage

Old Server

```text id="dbvs010"
Hard Disk
```

Upgrade

```text id="dbvs011"
NVMe SSD
```

Benefits:

- Faster reads
- Faster writes
- Faster WAL writes
- Faster backups
- Faster recovery

______________________________________________________________________

# Better Network

Suppose

```text id="dbvs012"
1 Gbps
```

Upgrade

```text id="dbvs013"
10 Gbps
```

Clients receive data more quickly.

______________________________________________________________________

# More Connections

Larger servers can typically handle more concurrent database connections because they have more CPU and memory
available.

However,

increasing `max_connections` alone is **not** a scaling strategy.

Connection pooling is still recommended.

______________________________________________________________________

# Advantages

Vertical Scaling is simple.

```text id="dbvs014"
No Code Changes

No Sharding

No Routing

No Replication
```

Your application continues using the same connection string.

______________________________________________________________________

# Single Point of Failure

One database server

↓

Hardware failure

↓

Everything stops.

This is the biggest weakness of vertical scaling.

______________________________________________________________________

# Maintenance

Suppose

You upgrade hardware.

Often,

the database must be restarted or migrated.

Downtime may be required unless you have replication or failover mechanisms.

______________________________________________________________________

# When Should You Use Vertical Scaling?

Good choice for:

- Small applications
- Medium-sized applications
- Internal tools
- MVPs
- Early-stage startups

It delays complexity while providing significant performance improvements.

______________________________________________________________________

# When Should You Stop?

If you experience:

- High CPU despite hardware upgrades
- Constant memory pressure
- Connection bottlenecks
- Very high read traffic
- Storage limits
- Availability requirements

it's time to consider horizontal scaling.

______________________________________________________________________

# Monitoring Before Scaling

Always check:

- CPU utilization
- RAM usage
- Query latency
- Disk I/O
- Cache hit ratio
- Slow queries
- Connection usage

Never upgrade hardware blindly.

Measure first.

______________________________________________________________________

# Common Mistakes

### Scaling Before Optimizing

Don't buy a larger server because of one poorly written query.

Optimize first.

______________________________________________________________________

### Ignoring Indexes

Indexes often improve performance more than hardware upgrades.

______________________________________________________________________

### Forgetting Connection Pooling

Even a powerful server can struggle with thousands of unnecessary connections.

______________________________________________________________________

### Assuming Bigger Hardware Solves Everything

Eventually,

every application reaches the limits of a single server.

______________________________________________________________________

# Best Practices

- Optimize queries first.
- Add indexes where needed.
- Monitor database performance.
- Use connection pooling.
- Upgrade hardware only after understanding the bottleneck.
- Delay architectural complexity until it's justified.

# Interview Deep Dive

## Answer

**Question:** Why don't large companies rely only on vertical scaling?

Vertical scaling is simple and effective, but it has practical limits. Hardware cannot be upgraded indefinitely, larger
servers become increasingly expensive, and a single database remains a single point of failure. It also doesn't
distribute read traffic across multiple machines or improve availability. As applications grow, companies typically
combine vertical scaling with horizontal scaling techniques such as read replicas, sharding, and partitioning.

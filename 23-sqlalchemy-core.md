# 1. What Is SQLAlchemy?

SQLAlchemy is a Python SQL toolkit and Object Relational Mapper (ORM).

It provides abstractions for working with relational databases while still allowing developers to work with SQL concepts
directly.

The ORM maps Python objects/classes to relational database structures.

Conceptually:

```text
Python class
     ↓
ORM mapping
     ↓
Database table
```

______________________________________________________________________

# 2. Why Use an ORM?

An ORM can provide:

- Object-oriented models
- Relationship management
- Unit-of-work behavior
- Identity management
- Transaction integration
- Database abstraction
- Query construction

However:

> An ORM does not remove the need to understand SQL.

A backend engineer should understand the SQL generated by important ORM operations.

______________________________________________________________________

# 3. SQLAlchemy Architecture

A simplified architecture is:

```text
Application
    ↓
ORM Session
    ↓
ORM / SQL expression layer
    ↓
Engine
    ↓
Connection / Pool
    ↓
DBAPI driver
    ↓
Database
```

Each layer has a different responsibility.

______________________________________________________________________

# 4. Engine

The `Engine` is the main entry point to a database in SQLAlchemy.

It coordinates:

- Database connectivity
- Connection pooling
- Dialect behavior
- DBAPI interaction

Example:

```python
from sqlalchemy import create_engine

engine = create_engine(
    "postgresql+psycopg://user:password@localhost/app"
)
```

The exact connection URL depends on the database and driver.

______________________________________________________________________

# 5. Engine Is Not a Single Database Connection

A common interview mistake is:

> "The Engine is the database connection."

More accurately, the Engine is a factory/coordinator for database connections and maintains access to a connection pool
in typical configurations.

Conceptually:

```text
Engine
  ↓
Connection Pool
  ↓
Database Connections
```

______________________________________________________________________

# 6. Connection

A `Connection` represents an active database connection used to communicate with the database.

At the Core level:

```python
with engine.connect() as connection:
    result = connection.execute(...)
```

The Connection is closer to direct database interaction than the ORM Session.

______________________________________________________________________

# 7. Session

The ORM `Session` provides the main interface for working with mapped objects.

It manages concepts such as:

- Identity map
- Unit of work
- Object state
- Transaction participation

Example:

```python
from sqlalchemy.orm import Session

with Session(engine) as session:
    ...
```

______________________________________________________________________

# 8. Session Is Not the Same as Connection

A useful distinction:

| Component | Responsibility |
|---|---|
| Engine | Database connectivity infrastructure |
| Connection | Active DB connection |
| Session | ORM object/unit-of-work management |

The Session may acquire connections from the Engine when database work is required.

______________________________________________________________________

# 9. Session Lifecycle

A typical application flow is:

```text
Create Session
     ↓
Load/create objects
     ↓
Modify objects
     ↓
Flush
     ↓
Commit
     ↓
Close
```

On failure:

```text
Rollback
     ↓
Close
```

The exact lifecycle depends on the application's architecture and framework integration.

______________________________________________________________________

# 10. Session Per Request

A common web-application pattern is:

```text
HTTP request
    ↓
Create Session
    ↓
Perform database work
    ↓
Commit/Rollback
    ↓
Close Session
    ↓
HTTP response
```

This gives each request a clear unit of ORM work.

The exact pattern depends on the framework and application architecture.

______________________________________________________________________

# 11. Session Should Not Be a Global Singleton

A common mistake is sharing one ORM Session globally across unrelated requests or threads.

A Session represents state associated with a unit of work.

Sharing it broadly can cause:

- Concurrency problems
- Stale object state
- Transaction confusion
- Unexpected identity-map behavior

Use an appropriate session lifecycle for the application.

______________________________________________________________________

# 12. Declarative Models

SQLAlchemy supports declarative ORM mappings.

Modern SQLAlchemy commonly uses:

```python
from sqlalchemy.orm import DeclarativeBase

class Base(DeclarativeBase):
    pass
```

A model can then be defined:

```python
from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column

class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True)
```

______________________________________________________________________

# 13. Model-to-Table Mapping

The model:

```python
class User(Base):
    ...
```

represents a mapped database table.

For example:

```text
User
 ↓
users
```

Attributes map to columns.

______________________________________________________________________

# 14. Primary Key

Example:

```python
id: Mapped[int] = mapped_column(primary_key=True)
```

The primary key gives each mapped object a database identity.

This is particularly important for SQLAlchemy's identity map.

______________________________________________________________________

# 15. Relationships

Suppose:

```text
User
  ↓
Orders
```

A SQLAlchemy relationship can represent that association.

Example:

```python
from sqlalchemy import ForeignKey
from sqlalchemy.orm import Mapped, mapped_column, relationship

class Order(Base):
    __tablename__ = "orders"

    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))

    user: Mapped["User"] = relationship(back_populates="orders")
```

And:

```python
class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)

    orders: Mapped[list["Order"]] = relationship(
        back_populates="user"
    )
```

______________________________________________________________________

# 16. Foreign Key vs Relationship

These concepts are related but different.

### Foreign key

Database-level relationship constraint:

```text
orders.user_id → users.id
```

### ORM relationship

Python-side mapping/navigation:

```python
order.user
user.orders
```

A relationship does not replace the need for an appropriate database foreign key.

______________________________________________________________________

# 17. Creating an Object

Example:

```python
user = User(
    email="alice@example.com"
)

session.add(user)
```

At this point, the object is associated with the Session.

It may not yet have been inserted into the database.

______________________________________________________________________

# 18. `session.add()`

`add()` places an object into the Session's unit of work.

It does not necessarily immediately execute an `INSERT`.

The SQL may be emitted during a flush.

______________________________________________________________________

# 19. Flush

`flush()` synchronizes pending ORM changes with the database within the current transaction.

Example:

```python
session.add(user)
session.flush()
```

The database may now have received:

```sql
INSERT INTO users ...
```

but the transaction has not necessarily been committed.

______________________________________________________________________

# 20. Flush vs Commit

This is one of the most important SQLAlchemy interview questions.

### `flush()`

```text
ORM state
   ↓
SQL statements sent to database
```

The transaction remains active.

### `commit()`

```text
Transaction
   ↓
Commit
```

The transaction is completed successfully.

Therefore:

> Flush is not commit.

______________________________________________________________________

# 21. Why Flush Matters

Suppose you create:

```python
user = User(email="alice@example.com")
session.add(user)
session.flush()
```

If the database generates the user's ID, SQLAlchemy may now know:

```python
user.id
```

even though the transaction has not committed yet.

This is useful when subsequent operations need the generated primary key.

______________________________________________________________________

# 22. Autoflush

SQLAlchemy can automatically flush pending changes before certain database operations.

For example, a query may trigger a flush depending on the Session's configuration and operation.

This is called autoflush.

The important interview point:

> A query can cause pending ORM changes to be flushed before the query executes.

______________________________________________________________________

# 23. Disabling Autoflush Temporarily

SQLAlchemy provides mechanisms such as:

```python
with session.no_autoflush:
    ...
```

This can be useful when pending changes should not be flushed before a particular operation.

Use it deliberately.

______________________________________________________________________

# 24. Commit

Example:

```python
session.add(user)
session.commit()
```

Commit completes the current transaction.

After a successful commit, SQLAlchemy's objects may also be expired depending on Session configuration.

The default behavior commonly expires state after commit so subsequent access can refresh from the database.

______________________________________________________________________

# 25. Rollback

If a database operation fails:

```python
try:
    session.add(user)
    session.commit()
except Exception:
    session.rollback()
    raise
```

Rollback ends the failed transaction and returns the Session to a usable transactional state.

______________________________________________________________________

# 26. Failed Session Transaction

A common SQLAlchemy mistake is:

```python
try:
    session.commit()
except Exception:
    pass

session.add(other_object)
session.commit()
```

After a flush/commit failure, the Session generally requires:

```python
session.rollback()
```

before continuing transactional work.

______________________________________________________________________

# 27. Transaction Context Manager

SQLAlchemy provides transaction context-manager patterns.

Conceptually:

```python
with Session(engine) as session:
    with session.begin():
        session.add(user)
```

If the block succeeds, the transaction is committed.

If an exception occurs, the transaction is rolled back.

______________________________________________________________________

# 28. CRUD — Create

Example:

```python
user = User(
    email="alice@example.com"
)

session.add(user)
session.commit()
```

For multiple objects:

```python
session.add_all([
    User(email="a@example.com"),
    User(email="b@example.com"),
])

session.commit()
```

______________________________________________________________________

# 29. CRUD — Read

Modern SQLAlchemy uses `select()` for ORM queries.

Example:

```python
from sqlalchemy import select

stmt = select(User).where(
    User.email == "alice@example.com"
)

user = session.scalar(stmt)
```

This keeps the query construction explicit.

______________________________________________________________________

# 30. `session.execute()` vs `session.scalar()`

For ORM queries:

```python
result = session.execute(stmt)
```

returns a result object.

If you expect one scalar ORM value:

```python
user = session.scalar(stmt)
```

can be convenient.

For multiple ORM objects:

```python
users = session.scalars(stmt).all()
```

______________________________________________________________________

# 31. CRUD — Update

Load an object:

```python
user = session.get(User, user_id)

user.email = "new@example.com"

session.commit()
```

SQLAlchemy tracks the change as part of the unit of work.

______________________________________________________________________

# 32. CRUD — Delete

Example:

```python
user = session.get(User, user_id)

if user:
    session.delete(user)

session.commit()
```

The Session tracks the deletion and emits the appropriate SQL during flush.

______________________________________________________________________

# 33. `session.get()`

For primary-key lookup:

```python
user = session.get(User, user_id)
```

This has an important ORM property:

> The Session's identity map participates in primary-key lookups.

If the object is already present in the Session's identity map, SQLAlchemy can return the existing object rather than
creating a second Python object for the same database identity.

______________________________________________________________________

# 34. Identity Map

The identity map maintains one ORM object instance per database identity within a Session.

Conceptually:

```text
Database row
    ↓
Primary key = 10
    ↓
Session identity map
    ↓
User Python object
```

Repeatedly loading the same row through the same Session can return the same object instance.

______________________________________________________________________

# 35. Why Identity Map Matters

Suppose:

```python
user1 = session.get(User, 10)
user2 = session.get(User, 10)
```

Within the same Session, SQLAlchemy can maintain:

```python
user1 is user2
```

for the same identity.

This prevents conflicting in-memory representations of the same database identity within the Session.

______________________________________________________________________

# 36. Identity Map Is Session-Scoped

The identity map belongs to the Session.

Different Sessions can have different Python objects representing the same database row.

For example:

```text
Session A → User(id=10)
Session B → User(id=10)
```

These are different Python object instances.

______________________________________________________________________

# 37. Unit of Work

The Session implements unit-of-work behavior.

It tracks changes such as:

```text
new objects
modified objects
deleted objects
```

and coordinates the SQL emitted during flush.

Conceptually:

```text
Python object changes
        ↓
Unit of work
        ↓
SQL INSERT/UPDATE/DELETE
```

______________________________________________________________________

# 38. Unit of Work Example

Suppose:

```python
user.name = "Alice Smith"
new_order = Order(...)
session.add(new_order)
session.delete(old_object)
```

At flush time, SQLAlchemy determines the required database operations.

This lets the application work with object state while SQLAlchemy coordinates persistence.

______________________________________________________________________

# 39. Object States

An ORM object can move through states such as:

```text
Transient
   ↓
Pending
   ↓
Persistent
   ↓
Detached
```

There are also deleted states during lifecycle transitions.

______________________________________________________________________

# 40. Transient

A newly created object not associated with a Session:

```python
user = User(email="a@example.com")
```

It is transient.

It has not been added to a Session.

______________________________________________________________________

# 41. Pending

After:

```python
session.add(user)
```

the object becomes pending.

It is associated with the Session but its INSERT may not have been flushed yet.

______________________________________________________________________

# 42. Persistent

After the object is flushed and associated with the current Session/identity map, it is persistent.

The object corresponds to database identity managed by the Session.

______________________________________________________________________

# 43. Detached

After the Session is closed or the object is otherwise removed from Session management, the object can become detached.

Detached objects may still contain loaded state but are no longer associated with that Session.

Accessing unloaded/expired attributes can cause problems depending on the state and configuration.

______________________________________________________________________

# 44. Session Lifecycle Summary

| State | Meaning |
|---|---|
| Transient | New Python object, not in Session |
| Pending | Added to Session, awaiting persistence |
| Persistent | Associated with Session/database identity |
| Detached | No longer associated with Session |
| Deleted | Marked for deletion as part of transaction lifecycle |

______________________________________________________________________

# 45. Relationship Loading

SQLAlchemy relationships can be loaded using different strategies.

Common concepts include:

- Lazy loading
- Joined eager loading
- Select-in eager loading

Example:

```python
relationship(
    "Order",
    lazy="selectin"
)
```

The details and performance implications are covered more deeply in File 24.

______________________________________________________________________

# 46. Connection Pooling

The Engine commonly manages a connection pool.

Conceptually:

```text
Application
    ↓
Engine
    ↓
Connection Pool
    ├── Connection
    ├── Connection
    ├── Connection
    └── Connection
```

A connection can be checked out for database work and returned to the pool when no longer needed.

______________________________________________________________________

# 47. Why Connection Pooling Exists

Creating a new database connection for every operation can be expensive.

Pooling allows connections to be reused.

Benefits can include:

- Lower connection-establishment overhead
- Controlled concurrency
- Better resource utilization
- Reduced database connection churn

______________________________________________________________________

# 48. Pool Size

A pool commonly has configuration such as:

```text
pool size
overflow
timeout
```

Exact options depend on the SQLAlchemy pool implementation and database environment.

Do not configure these numbers blindly.

______________________________________________________________________

# 49. Connection Pool vs Session

These are different concerns.

### Pool

Manages database connections.

### Session

Manages ORM state and unit-of-work behavior.

Conceptually:

```text
Session
  ↓
gets connection when needed
  ↓
Engine / Pool
  ↓
Database
```

A Session is not a connection pool.

______________________________________________________________________

# 50. Transactions and Session

A Session participates in database transactions.

A simplified flow:

```text
Session
  ↓
begin transaction
  ↓
flush SQL
  ↓
commit
```

If an error occurs:

```text
rollback
```

The actual transaction lifecycle depends on the operations and SQLAlchemy configuration.

______________________________________________________________________

# 51. Commit Does Not Mean "Save Every Object Immediately"

SQLAlchemy tracks ORM state.

When you call:

```python
session.commit()
```

pending changes are normally flushed before the transaction commits.

Therefore:

```text
object changes
   ↓
flush
   ↓
commit
```

______________________________________________________________________

# 52. Flush Can Fail

A flush can fail because of:

- Unique constraint violation
- Foreign key violation
- `NOT NULL` violation
- Database errors
- Invalid SQL/data

If flush fails, the transaction is generally considered failed and the Session needs rollback before continuing.

______________________________________________________________________

# 53. Rollback Does Not Mean Objects Never Changed

Rollback affects the database transaction.

The Session may also expire or restore object state according to SQLAlchemy's behavior/configuration.

Do not assume every Python-side mutation simply disappears in every object state.

The important rule:

> After transaction failure, rollback the Session and then carefully reason about object state before continuing.

______________________________________________________________________

# 54. Nested Transactions — Overview

SQLAlchemy supports patterns for savepoints using:

```python
session.begin_nested()
```

This can create a database savepoint where supported.

Conceptually:

```text
Outer transaction
    ↓
Savepoint
    ↓
Nested work
    ↓
Rollback to savepoint
    ↓
Continue outer transaction
```

This is different from creating an independent database transaction.

______________________________________________________________________

# 55. Session and Threads

A normal SQLAlchemy Session should not be treated as a thread-safe shared object.

A common backend design is:

```text
Request/thread/task
      ↓
its appropriate Session
```

rather than one global Session shared across concurrent execution.

The exact concurrency pattern depends on whether the application uses threads, async tasks or another execution model.

______________________________________________________________________

# 56. Async SQLAlchemy — Overview

SQLAlchemy also provides async APIs.

Conceptually:

```text
AsyncSession
     ↓
AsyncEngine
     ↓
Async database driver
```

The async API is different from simply running synchronous SQLAlchemy calls inside `async def`.

For this course, understand the distinction; deeper async SQLAlchemy performance patterns can be covered later when
relevant to FastAPI.

______________________________________________________________________

# 57. ORM and Database Transactions

SQLAlchemy does not replace database transaction semantics.

The database remains responsible for:

- ACID guarantees
- Isolation
- Locks
- MVCC
- Constraint enforcement

SQLAlchemy provides application-level abstractions for working with those database capabilities.

______________________________________________________________________

# 58. ORM and SQL

Always remember:

```text
ORM operation
    ↓
SQL generated
    ↓
Database executes SQL
```

For example:

```python
user.email = "new@example.com"
session.commit()
```

may ultimately result in an SQL `UPDATE`.

Understanding this relationship is critical for debugging performance and correctness.

______________________________________________________________________

# 59. Common SQLAlchemy Architecture

A practical Python backend may use:

```text
API
 ↓
Service
 ↓
Repository / data-access layer
 ↓
SQLAlchemy Session
 ↓
Database
```

The exact architecture varies.

The important point is to define clear transaction ownership rather than allowing every function to commit
independently.

______________________________________________________________________

# 60. Transaction Ownership

A common design problem is:

```python
def create_user():
    session.add(user)
    session.commit()
```

while another service operation needs:

```text
create_user
+
create_profile
+
create_audit_log
```

to be atomic.

If each repository commits independently, the larger business operation becomes difficult to make atomic.

A better design often lets a higher-level service/application boundary own the transaction.

______________________________________________________________________

# 61. Repository vs Service Transaction Boundary

Conceptually:

```text
Service
  ↓
BEGIN
  ↓
Repository A
Repository B
Repository C
  ↓
COMMIT
```

rather than:

```text
Repository A → COMMIT
Repository B → COMMIT
Repository C → COMMIT
```

when all operations belong to one atomic business operation.

______________________________________________________________________

# 62. Connection Lifecycle

A connection is typically:

```text
Pool
 ↓
Checkout
 ↓
Database work
 ↓
Transaction operations
 ↓
Return to pool
```

The application should avoid holding connections longer than necessary.

Long-running transactions can also hold connections for longer periods.

______________________________________________________________________

# 63. Pool Exhaustion

If all available connections are checked out and held too long, new requests may wait for a connection.

Symptoms can include:

- Request latency
- Connection timeout errors
- Reduced throughput

Possible causes include:

- Too many concurrent requests
- Long transactions
- Slow queries
- Connection leaks
- Incorrect pool sizing

______________________________________________________________________

# 64. Connection Leak

A connection/session lifecycle bug can prevent resources from being returned correctly.

In web applications, use appropriate context-management/dependency patterns so sessions are reliably cleaned up.

______________________________________________________________________

# 65. SQLAlchemy CRUD Example

A simplified complete flow:

```python
from sqlalchemy import select
from sqlalchemy.orm import Session

def create_and_get_user(engine):
    with Session(engine) as session:
        user = User(email="alice@example.com")
        session.add(user)

        session.flush()

        user_id = user.id

        session.commit()

        return user_id
```

The important sequence is:

```text
add
 ↓
flush
 ↓
commit
 ↓
close
```

______________________________________________________________________

# 66. Transactional CRUD Example

Multiple changes:

```python
with Session(engine) as session:
    try:
        user = User(email="alice@example.com")
        session.add(user)

        order = Order(user=user)
        session.add(order)

        session.commit()
    except Exception:
        session.rollback()
        raise
```

Both changes belong to the same transaction.

A context-managed transaction can make this pattern cleaner.

______________________________________________________________________

# 67. Error Handling

A production application should distinguish:

- Validation errors
- Constraint violations
- Connection errors
- Transaction/concurrency errors
- Programming errors

Do not convert every database exception into the same application response.

______________________________________________________________________

# 68. Unique Constraint Example

Suppose:

```text
email UNIQUE
```

Two requests attempt:

```text
alice@example.com
```

One may succeed while the other receives a database constraint violation.

Application code should handle the expected business outcome appropriately.

A pre-check such as:

```text
SELECT email
```

does not replace the unique database constraint because concurrent requests can race.

______________________________________________________________________

# 69. ORM Identity vs Database Identity

The Session's identity map uses database identity, normally based on the primary key.

The Python object identity:

```python
id(user)
```

and database identity:

```text
user.id
```

are different concepts.

SQLAlchemy uses database identity to manage ORM identity within the Session.

______________________________________________________________________

# 70. Session Expiration

SQLAlchemy may expire object state after commit depending on configuration.

If expired state is accessed while the object remains associated with an active Session, SQLAlchemy can refresh it from
the database.

This behavior is important when reasoning about:

- Detached objects
- Lazy loading
- Request/session boundaries

______________________________________________________________________

# 71. Detached Object Problem

Consider:

```python
with Session(engine) as session:
    user = session.get(User, 1)

# session closed

print(user.orders)
```

If `orders` was not loaded and requires a database query, the detached object may not be able to load it.

This is one reason session lifecycle and relationship-loading strategy matter.

Deeper relationship performance is covered in File 24.

______________________________________________________________________

# 72. Common SQLAlchemy Mistakes

## Mistake 1 — Confusing Session and Connection

They solve different problems.

## Mistake 2 — Assuming `add()` immediately executes SQL

Changes are normally synchronized during flush.

## Mistake 3 — Confusing `flush()` and `commit()`

Flush sends changes to the database within the transaction.

Commit completes the transaction.

## Mistake 4 — Forgetting rollback after failure

A failed transaction generally requires rollback before continuing.

## Mistake 5 — Global Session

Sharing one Session across concurrent requests/tasks is unsafe.

## Mistake 6 — Repository commits everywhere

This can break larger transaction boundaries.

## Mistake 7 — Ignoring generated SQL

ORM abstractions do not eliminate SQL performance considerations.

## Mistake 8 — Creating excessive connections

Connection pooling should be configured according to workload.

# 73. Interview Questions & Answers

## Q1. What is SQLAlchemy?

**Answer:**

SQLAlchemy is a Python SQL toolkit and ORM that provides database connectivity, SQL construction and object-relational
mapping.

______________________________________________________________________

## Q2. What is the Engine?

**Answer:**

The Engine coordinates database connectivity, dialect behavior, DBAPI interaction and connection pooling.

______________________________________________________________________

## Q3. Is the Engine a database connection?

**Answer:**

No.

It is a higher-level database connectivity object that typically manages access to a pool of connections.

______________________________________________________________________

## Q4. What is a Connection?

**Answer:**

An active database connection used to execute database operations.

______________________________________________________________________

## Q5. What is a Session?

**Answer:**

The ORM Session manages mapped objects, identity-map behavior, unit-of-work state and participation in transactions.

______________________________________________________________________

## Q6. Session vs Connection?

**Answer:**

A Connection represents direct database connectivity.

A Session manages ORM object state and unit-of-work behavior and obtains connections from the Engine as needed.

______________________________________________________________________

## Q7. What does `session.add()` do?

**Answer:**

It associates an object with the Session and marks it for persistence.

It does not necessarily execute the `INSERT` immediately.

______________________________________________________________________

## Q8. What does `flush()` do?

**Answer:**

It synchronizes pending ORM changes with the database by emitting required SQL within the current transaction.

______________________________________________________________________

## Q9. What is the difference between flush and commit?

**Answer:**

Flush sends pending SQL to the database but does not complete the transaction.

Commit completes the transaction.

______________________________________________________________________

## Q10. Why would you call `flush()` explicitly?

**Answer:**

One reason is to make pending changes visible to the current transaction/database and obtain database-generated values
such as a generated primary key before committing.

______________________________________________________________________

## Q11. What is autoflush?

**Answer:**

SQLAlchemy can automatically flush pending changes before certain operations, such as queries, depending on Session
behavior/configuration.

______________________________________________________________________

## Q12. What does `commit()` do?

**Answer:**

It commits the current database transaction after pending changes have been flushed as necessary.

______________________________________________________________________

## Q13. What does `rollback()` do?

**Answer:**

It rolls back the current failed/uncommitted transaction and returns the Session to a state where transactional work can
continue after the failure is handled.

______________________________________________________________________

## Q14. What happens if you don't rollback after a failed flush?

**Answer:**

The Session generally remains in a failed transaction state and requires an explicit rollback before further
transactional work can proceed.

______________________________________________________________________

## Q15. What is the identity map?

**Answer:**

A Session-scoped mechanism that maintains a unique ORM object instance for a given database identity within that
Session.

______________________________________________________________________

## Q16. Why is the identity map useful?

**Answer:**

It prevents multiple in-memory ORM objects in the same Session from representing the same database identity
independently.

______________________________________________________________________

## Q17. Is the identity map global?

**Answer:**

No.

It is associated with a Session.

______________________________________________________________________

## Q18. What is the unit-of-work pattern?

**Answer:**

It tracks object changes and coordinates the SQL operations required to persist those changes as part of a transaction.

______________________________________________________________________

## Q19. What are common SQLAlchemy object states?

**Answer:**

Transient, pending, persistent and detached, with deleted being another lifecycle state.

______________________________________________________________________

## Q20. What is a transient object?

**Answer:**

A newly created Python ORM object that is not associated with a Session.

______________________________________________________________________

## Q21. What is a pending object?

**Answer:**

An object added to a Session but not yet persisted to the database through a flush.

______________________________________________________________________

## Q22. What is a persistent object?

**Answer:**

An ORM object associated with a Session and having database identity managed by that Session.

______________________________________________________________________

## Q23. What is a detached object?

**Answer:**

An ORM object that is no longer associated with its Session.

______________________________________________________________________

## Q24. What is a relationship?

**Answer:**

An ORM mapping that represents an association between mapped objects, such as `User.orders`.

______________________________________________________________________

## Q25. Foreign key vs relationship?

**Answer:**

A foreign key is a database-level relationship constraint.

An ORM relationship provides Python-side object navigation/mapping.

______________________________________________________________________

## Q26. How do you create an ORM record?

**Answer:**

Create the mapped object, add it to the Session and commit the transaction.

______________________________________________________________________

## Q27. How do you query an object by primary key?

**Answer:**

Use:

```python
session.get(Model, primary_key)
```

______________________________________________________________________

## Q28. Why is `session.get()` special?

**Answer:**

It is designed for primary-key retrieval and works with the Session's identity map.

______________________________________________________________________

## Q29. How do you update an ORM object?

**Answer:**

Load it, modify its attributes and commit the transaction. SQLAlchemy tracks the changes and emits the update during
flush.

______________________________________________________________________

## Q30. How do you delete an ORM object?

**Answer:**

Call:

```python
session.delete(obj)
```

and commit the transaction.

______________________________________________________________________

## Q31. What is connection pooling?

**Answer:**

A mechanism for reusing database connections rather than establishing a new connection for every database operation.

______________________________________________________________________

## Q32. Why use connection pooling?

**Answer:**

It reduces connection-establishment overhead and allows controlled reuse of database connections.

______________________________________________________________________

## Q33. Session vs connection pool?

**Answer:**

A Session manages ORM state and unit-of-work behavior.

A connection pool manages database connections.

______________________________________________________________________

## Q34. What happens when a pool is exhausted?

**Answer:**

Requests needing connections may wait until one becomes available or eventually receive a pool timeout, depending on
configuration.

______________________________________________________________________

## Q35. What causes pool exhaustion?

**Answer:**

Possible causes include long-running queries/transactions, connection leaks, excessive concurrency, incorrect pool
sizing or blocked database operations.

______________________________________________________________________

## Q36. Should a Session be shared between threads?

**Answer:**

A normal Session should not be treated as a thread-safe shared object. Use an appropriate Session per unit of
work/request/task.

______________________________________________________________________

## Q37. Why shouldn't repositories always call `commit()`?

**Answer:**

Because multiple repository operations may need to participate in one larger atomic business transaction. Higher-level
application/service code often needs transaction ownership.

______________________________________________________________________

## Q38. What is a good transaction-boundary pattern?

**Answer:**

A service/application layer can own the transaction while repositories perform database operations within that
transaction.

______________________________________________________________________

## Q39. What is `begin_nested()`?

**Answer:**

It can establish a savepoint within an existing transaction where supported. It is not the same as creating an
independent database transaction.

______________________________________________________________________

## Q40. Does SQLAlchemy replace database transactions?

**Answer:**

No.

SQLAlchemy provides abstractions for managing database work, but the database still provides transaction semantics,
isolation, locks, MVCC and durability.

______________________________________________________________________

## Q41. Does ORM knowledge eliminate the need for SQL knowledge?

**Answer:**

No.

ORM operations generate SQL and can still produce inefficient queries or unexpected database behavior.

______________________________________________________________________

## Q42. What is a common SQLAlchemy performance mistake?

**Answer:**

Ignoring generated SQL, especially when relationships or loops cause excessive database queries. Detailed performance
patterns are covered in File 24.

______________________________________________________________________

## Q43. What is autoflush?

**Answer:**

Automatic synchronization of pending ORM changes before certain operations.

______________________________________________________________________

## Q44. Why can flush fail?

**Answer:**

Because of database constraint violations, invalid data, connectivity problems or other database errors.

______________________________________________________________________

## Q45. What should you do after a failed flush?

**Answer:**

Rollback the Session's failed transaction before attempting further transactional work.

______________________________________________________________________

## Q46. Why can a detached object fail when accessing a relationship?

**Answer:**

If the relationship was not already loaded, SQLAlchemy may need the Session to execute another query. A detached object
has no active Session through which to perform that load.

______________________________________________________________________

## Q47. What is `expire_on_commit` conceptually?

**Answer:**

It controls whether ORM state is expired after commit so that later access can refresh values from the database. The
default behavior commonly expires state.

______________________________________________________________________

## Q48. What is the difference between database identity and Python object identity?

**Answer:**

Database identity is typically determined by a primary key.

Python object identity is the identity of the in-memory object itself.

SQLAlchemy's identity map connects database identity to a Session-scoped ORM object.

______________________________________________________________________

## Q49. What is the Engine responsible for?

**Answer:**

Connectivity infrastructure, dialect/driver integration and connection-pool management.

______________________________________________________________________

## Q50. Give a senior-level explanation of SQLAlchemy Session management.

**Answer:**

Treat the Session as a unit-of-work/ORM state boundary, give it a clear lifecycle such as per request or business
operation, keep transaction ownership explicit, rollback after failures, avoid sharing it across concurrent units of
work and inspect generated SQL for important workloads.

______________________________________________________________________

# 74. Scenario-Based Questions

## Scenario 1 — Flush vs Commit

You call:

```python
session.add(user)
session.flush()
```

The user receives an ID.

**Question:** Is the data committed?

**Answer:**

No.

Flush synchronizes the insert with the database inside the current transaction. The transaction still needs to be
committed.

______________________________________________________________________

## Scenario 2 — Failed Commit

A unique constraint violation occurs during commit.

**Question:** What should happen before the Session is reused?

**Answer:**

Rollback the failed transaction.

______________________________________________________________________

## Scenario 3 — Repository Commits

You have:

```text
create_user()
create_profile()
create_audit()
```

Each repository function calls `commit()`.

**Question:** Why can this be a problem?

**Answer:**

The operations cannot easily participate in one larger atomic transaction because each function commits independently.

Move transaction ownership to an appropriate higher-level boundary.

______________________________________________________________________

## Scenario 4 — Same User Loaded Twice

You run:

```python
a = session.get(User, 1)
b = session.get(User, 1)
```

**Question:** What should you understand about `a` and `b`?

**Answer:**

Within the same Session and identity, SQLAlchemy's identity map can return the same ORM object instance.

______________________________________________________________________

## Scenario 5 — Global Session

A FastAPI application creates one global Session and all requests share it.

**Question:** What is wrong?

**Answer:**

The Session is a stateful unit-of-work object and should not be treated as a globally shared concurrent Session. Use an
appropriate per-request/task lifecycle.

______________________________________________________________________

## Scenario 6 — Pool Exhaustion

API latency suddenly increases and requests begin timing out waiting for database connections.

**Question:** What would you investigate?

**Answer:**

Check:

- Pool configuration
- Connection checkout duration
- Long-running transactions
- Slow queries
- Session/connection leaks
- Concurrent request volume

______________________________________________________________________

## Scenario 7 — Detached Relationship

You load a `User`, close the Session, then access:

```python
user.orders
```

and receive a detached-instance-related error.

**Question:** Why?

**Answer:**

The relationship was not loaded before the Session closed, so SQLAlchemy needs a Session to issue the relationship
query.

______________________________________________________________________

## Scenario 8 — Generated SQL

A simple-looking ORM loop causes hundreds of SQL statements.

**Question:** What should you do?

**Answer:**

Inspect the generated SQL and identify whether relationship loading or another ORM pattern is producing excessive
queries.

File 24 covers this performance topic in more depth.

______________________________________________________________________

## Scenario 9 — Atomic Business Operation

You need:

```text
create order
decrease inventory
create audit record
```

to succeed or fail together.

**Question:** Where should the transaction boundary live?

**Answer:**

At a higher-level business/service boundary that encompasses all required database operations.

______________________________________________________________________

## Scenario 10 — Explicit Flush

You create a parent object and need its database-generated ID before creating related records.

**Question:** What can you use?

**Answer:**

Explicitly flush the Session so the insert is sent to the database and generated identity values can become available,
while keeping the transaction uncommitted until the complete business operation is ready to commit.

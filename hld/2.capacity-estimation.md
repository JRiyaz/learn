# 1. Introduction

One of the biggest mistakes candidates make is jumping directly into architecture.

Interviewer:

> Design WhatsApp.

Candidate:

```
Load Balancer

↓

API

↓

Redis

↓

Kafka
```

The interviewer immediately thinks:

> "This person is designing a solution without understanding the problem."

A senior engineer always starts by understanding the business problem.

Think like an architect.

Before building a house, you ask:

- How many rooms?
- How many floors?
- Budget?
- Timeline?

Exactly the same applies to software.

______________________________________________________________________

# 2. Why Requirement Gathering Matters

Requirement gathering serves four purposes.

## 1. Defines Scope

Without scope,

you might design

an entire platform

when the interviewer only wants one feature.

Example:

Design Instagram.

Possible scopes:

- Upload Photos
- News Feed
- Search
- Messaging
- Entire Platform

Never assume.

______________________________________________________________________

## 2. Prevents Wrong Assumptions

Example

Suppose

the interviewer says

Design Netflix.

Questions:

- Live streaming?
- On-demand streaming?
- Downloads?
- Recommendations?
- Global platform?

Different requirements

lead to

different architectures.

______________________________________________________________________

## 3. Shows Senior-Level Thinking

Interviewers evaluate:

- Communication
- Prioritization
- Trade-offs
- Product thinking

Not just technical knowledge.

______________________________________________________________________

## 4. Saves Time

System Design interviews usually last 45–60 minutes.

Spending

5–10 minutes

on requirement gathering

prevents

30 minutes

of redesign later.

______________________________________________________________________

# 3. Interview Strategy

A simple strategy:

```
Understand

↓

Clarify

↓

Prioritize

↓

Estimate

↓

Design
```

Never skip the first three steps.

______________________________________________________________________

# 4. Requirement Gathering Framework

Always follow this sequence.

```
Problem

↓

Functional Requirements

↓

Non-Functional Requirements

↓

Scale

↓

Constraints

↓

Assumptions

↓

Confirm Scope

↓

Start Designing
```

Memorize this framework.

It works for almost every interview.

# 5. Functional Requirements

Functional requirements answer:

> What should the system do?

Examples:

For WhatsApp

- Send message
- Receive message
- Group chat
- Online status

For YouTube

- Upload videos
- Watch videos
- Search
- Like
- Subscribe

For Uber

- Request ride
- Accept ride
- Track driver
- Make payment

______________________________________________________________________

## Questions to Ask

### User Actions

Examples:

- What can users do?
- Read?
- Write?
- Delete?
- Update?

______________________________________________________________________

### CRUD Operations

Think:

- Create
- Read
- Update
- Delete

______________________________________________________________________

### Core Features

Ask:

> Which features should we focus on today?

Example:

Design Amazon.

Possible answers:

- Search
- Checkout
- Recommendation
- Inventory

______________________________________________________________________

### APIs

Think about:

```
POST

GET

PUT

DELETE
```

You don't need to design them yet,

just understand them.

# 6. Non-Functional Requirements

These describe

how the system behaves.

Examples:

- Scalability
- Availability
- Reliability
- Durability
- Consistency
- Latency
- Security

______________________________________________________________________

## Scalability

Ask:

Expected users?

Expected traffic?

Growth?

Example:

```
100 users

vs

100 Million users
```

Architecture changes completely.

______________________________________________________________________

## Availability

Ask:

Should the service

remain available

during failures?

Examples:

- Banking → Very High
- WhatsApp → Very High
- Analytics → Medium

______________________________________________________________________

## Consistency

Ask:

Should users

always see

the latest data?

Example:

Bank Account

Strong consistency.

Instagram Likes

Eventual consistency

is acceptable.

______________________________________________________________________

## Latency

Ask:

Expected response time?

Examples:

Search

\<200ms

Chat

\<100ms

Payments

Correctness

is more important

than speed.

______________________________________________________________________

## Durability

Question:

Can we lose data?

Payments

No.

Analytics logs

Maybe acceptable.

______________________________________________________________________

## Security

Questions:

Authentication?

Authorization?

Encryption?

Compliance?

PII?

# 7. Scope Definition

One of the most important interview skills.

Suppose

Interviewer:

Design Twitter.

Bad response:

```
Messaging

Feed

Search

Ads

Videos

Analytics

Spaces

Notifications

Recommendations
```

Impossible

in one interview.

Instead say:

> I'd like to focus on Tweet posting and Timeline generation.

Interviewer usually agrees.

Now

you have

a well-defined scope.

______________________________________________________________________

# 8. Out of Scope

Explicitly mention

what you're not designing.

Example:

Design URL Shortener.

Out of scope:

- Analytics
- Custom URLs
- QR Codes
- User Authentication

This shows

good prioritization.

______________________________________________________________________

# 9. Requirement Prioritization

Classify requirements.

### Must Have

Core functionality.

### Should Have

Useful,

but optional.

### Nice to Have

Future improvements.

Example:

WhatsApp

Must

- Send messages

Should

- Read receipts

Nice

- Message reactions

# Quick Cheat Sheet

Whenever the interviewer gives a problem, ask yourself:

1. What exactly am I building?
1. Which features are in scope?
1. Which features are out of scope?
1. Who are the users?
1. How many users?
1. Read-heavy or write-heavy?
1. Strong consistency or eventual consistency?
1. Expected latency?
1. Availability requirements?
1. Any security or compliance requirements?
1. Any storage constraints?
1. Any technology constraints?

If you can answer these questions, you've completed requirement gathering like a senior engineer.
